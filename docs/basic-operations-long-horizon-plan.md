## 1. 阶段目标与范围

在 Java 1.21.1 原版测试环境中，让 LLM 能查询制作知识、依据公开观测选择目标、指定基本操作与参数，并通过多轮观察和执行完成持续目标。首个纵向切片为“已有原木 → 制作并放置工作台 → 制作并装备木镐”；随后验证“空背包 → 石镐”和明确列出产物的木制工具套装。

基本操作包括观测、导航、停止、装备、挖掘、拾取、放置、合成、容器存取和熔炼。交易、附魔、酿造、复杂载具、建造体系、多 Bot、Node-RED 画布与基准协议适配放在后续阶段。现有七个组合技能继续作为可选便捷工具，基本操作接口允许模型更细地指定操作。

本计划不宣称当前合成故障已定位，不把配方查询成功当作游戏合成成功，也不把递归材料计算当作完整长程规划。

## 2. 查询数据源与 JEI 决策

### 本地数据优先

当前 `recipes` 查询使用 `bot.recipesFor`，会过滤材料不足的配方；因此空结果无法说明目标没有配方。Mineflayer 还提供 `recipesAll`，可忽略材料是否足够，但仍按工作台参数过滤。查询层应使用独立的“设施种类”参数查询理论配方，或直接使用当前版本 `prismarine-recipe` 的 `Recipe.find`；理论查询不得伪造一个已观测工作台。

2026-11-01 在本地使用 1.21.1 注册表和 Mineflayer 的依赖执行只读探针：可查询到云杉木板、木棍、工作台、木镐和石镐；木镐返回 `requiresTable=true`。探针还发现木棍第一条为竹子配方，工作台/木镐第一条使用樱花木板，石镐第一条使用深板岩圆石。这是离线数据探针，不是实机验证；它说明候选配方的顺序不能充当规划策略。

本地规则属于指定版本的知识，不自动代表服务器数据包、插件或模组的真实配方。每个结果都要声明来源、版本、修订和支持的加工种类；未收录的加工方式返回 `unknown` / `unsupported`。执行前继续核对当前材料与设施。

### JEI 为可选桥接数据源

JEI 1.21/1.21.1 官方文档提供 Java `IModPlugin`、`onRuntimeAvailable` 和 `IJeiRuntime` 接入方式，并支持原版与自定义配方类别。当前 Mineflayer 是独立 Node.js 客户端，不能直接调用另一个 Minecraft Java 客户端中的这些对象。设计判断：若需要 JEI，应新增客户端 Java 桥接模组，在匹配的游戏版本、加载器和模组包中运行，通过本机接口或导出快照向 SIM 提供只读知识；官方文档没有给出供本项目直接使用的通用 HTTP 服务。

桥接调研需核对实际 JEI API 版本，验证原料候选、标签、数量、产物、设施、耗时及特殊组件能否完整导出。自定义机器类别可能需要专用适配，不能假定所有 JEI 展示对象都可自动变成可执行配方。外部 Java 客户端的视野和背包不作为 Bot 的观测；只共享配方知识。查询到模组配方也不代表 Mineflayer 已支持对应网络协议或机器 GUI。

当前阶段先预留 `RecipeProvider`，实现本地原版数据源。若实际服务器有自定义配方，再按环境选择服务器公开规则导出或 JEI 桥接；这是可触发的兼容分支，不阻塞原版切片。

### 百科用于补充知识

公开百科适合补充采集条件、工具等级、掉落规则、燃料和操作说明。缺失或未知知识可以触发按需查询；返回来源 URL、适用版本、检索时间与待验证状态并缓存。网页文本只作为外部资料，不作为执行指令，也不能证明附近存在某资源或某次操作成功。

冲突处理：已核实的当前服务器规则优先于匹配版本的本地规则；百科冲突保留说明，不能静默覆盖。网页说明不能直接生成未校验的底层写操作。

## 3. 递归依赖查询

新增只读能力：`recipe_lookup`（理论配方）、`recipe_evaluate`（指定配方与数量的可行性）、`requirements_expand`（有界递归需求展开）。名称和字段为拟议契约，实施时统一维护 schema、目录与生成 JSON Schema。

拟议返回内容：`recipeRef`、来源/版本/修订、输入原料及候选、每次产量、设施要求、加工种类、所需批次、缺料、库存预留、剩余产物、依赖节点、未解决的获取需求和截断原因。区分“新增 N 个”与“最终持有 N 个”，避免把现有库存和增量目标混用。

递归展开规则：

1. 先扣除可用库存，跨分支预留同一批材料，防止重复分配。
2. 按每次产量向上取整计算批次，保留多余产物供后续分支使用。
3. 比较替代配方，优先利用已有材料与设施；返回选择依据，允许 LLM 显式指定或更换配方。
4. 处理工作台、熔炉等可复用设施；设施只制作一次，但放置、燃料、获取工具等另有条件。材料被工具需求循环依赖时应终止并报告。
5. 使用当前路径检测转换环（例如锭与块），同时设置深度、候选分支、节点、耗时和输出大小预算；不可用全局 visited 简单丢掉共享依赖。达到预算返回不完整结果。
6. 原木、圆石等无法进一步合成的材料形成“待获取”叶子。查询只声明需求，采集目标由规划器根据观测选择。工具耐久、采集等级、燃料等获取依赖单独建模。
7. 查询支持取消且不执行游戏写操作；展开结果是候选依赖图，执行前仍需重新验证。供 LLM 多轮追问子节点，避免一次传送整棵大图。

第一版覆盖原版徒手/工作台合成；熔炼、燃料和采集规则随后按 provider 的能力声明接入，不伪造缺失的完整规则。

## 4. 分阶段实施与验收

### P0：定位并修复基本操作的实机问题

优先合成与库存对账，再处理放置、拾取和导航。相关文件：`src/actions.ts`、`src/extensions.ts`、`src/observation.ts`、`src/control.ts` 与动作测试。

- 为合成记录请求配方/批次、操作前后物品计数、相关槽位与光标状态、窗口更新、API 完成和取消时间；原始槽位证据保留程序端，不全部发给模型。
- 验证徒手/工作台合成中的客户端预测、服务器更新和最终验收时序。以事件和有界对账解决已证实的问题，避免仅加固定休眠或盲目重试。
- 失败返回结构化的已观察变化、未确认部分及是否需要对账；结果不确定时先对账，不重放有消耗的动作。
- 保留取消检查和单 Bot 单执行器；在途原生操作结束前不释放控制权。

验收：在固定测试服分别重复木板、木棍、工作台、木镐制作各 5 次，逐次记录输入与产物；测试材料不足、取消和断线。每次实际尝试都计入记录，失败不能从分母删除。新发现缺陷有对应回归。未连接服务器时仅标记模拟验证。

### P1：实现配方知识与递归需求查询

新增 `RecipeProvider` 与递归需求服务；更新查询 schema、动作目录与模型工具卡。保留旧 `recipes` 的默认语义，新增接口或显式模式区分理论与当前可制作查询。

- 按注册表版本解析材料，区分设施要求与设施现存状态。
- 返回完整候选和稳定配方引用；有界展开并计算共享材料、批次和余量。
- 用竹子/木板木棍、不同木材、不同石材等实际替代配方验证选择，不依赖 `recipes[0]`。
- 熔炼和燃料数据单独核对覆盖范围，未收录时明确说明。

验收：空背包也可查到木镐配方及工作台要求；仅有云杉原木时依赖展开能选择云杉材料链；多工具目标不会重复花费同一批木板；已有工作台不重复计入制作；循环与预算耗尽有明确结果。查询不产生游戏副作用。

### P2：开放 LLM 可指定的基本操作

相关文件：`src/brain-contract.ts`、`src/brain-context.ts`、`src/brain-decision.ts`、`src/controller.ts`、`src/skills.ts` 与 `src/planner.ts`。

- 提供统一工具目录，标注查询/写操作、参数、前置条件、完成证据、版本限制、取消与部分效果；模型可选择组合技能，也可指定基本操作。
- 先开放观测/配方/需求查询、导航、装备、挖掘、拾取、放置、合成、容器和熔炉相关接口；其余动作按已验证版本逐项开放。
- 所有写调用仍编译到 TaskScheduler → ActionController → 同一 MinecraftActions / ActionExecutor，模型不执行任意代码或直接持有 Bot。
- 合成支持显式选择 `recipeRef`，执行端核对同一配方和 revision，不重新悄悄选择第一条；保留旧调用的兼容行为。
- 查询返回有 session、维度、观测修订/时效的引用；允许从玩家授权目标及 Bot 公开观测中选取目标。执行前复查过期引用和放置位置，替代“只有玩家说过坐标才可操作”的限制。
- 工具结果可在后续轮次引用，批次内结果绑定要有类型和失败处理；默认在需要新事实时结束本批次，交给模型重新观察。

验收：LLM 能选取观察到的工作台；没有工作台时能装备并放置已有工作台；能用选定配方完成合成。伪造/过期引用拒绝，观察到的合法引用可用；所有写操作保持互斥并响应停止。

### P3：持续目标与滚动规划

相关文件：`src/goals.ts`、`src/interaction.ts`、`src/brain-feedback.ts`、`src/planner.ts` 与 `src/scheduler.ts`。

- 将玩家持续目标与当前短批次分开：目标保存成功条件、里程碑、进度、未解决依赖、失败摘要和预算；短批次只执行当前有依据的步骤。
- 查询完成、批次完成、部分失败和观测变化都可触发下一轮决策，替换当前“仅一次 run_finished 跟进”的限制。目标成功条件由程序检查，模型回复不能结束或伪造目标成功。
- LLM 选择策略、配方、获取方式及基本操作；确定性服务计算材料与批次、校验依赖和证据。
- 每轮用真实执行结果更新剩余需求，重新展开受影响分支；合成不确定先对账，目标变化后重新选择。长目标采用独立时间/操作/模型调用预算，保留短批次预算。
- 针对无进展、相同状态下重复失败和反复切换策略设限；材料或设施已变化时允许合理重试。不能仅增加 4 步/120 秒上限来宣称支持长程规划。
- stop/cancel 中止模型与执行，不自动恢复；暂停后保留目标，恢复前重读世界。自主推进只限当前授权目标，不在完成后自行追加任务。
- 回复中的“开始/重试”由已提交任务的程序回执产生；模型只表达建议或事实，避免口头执行。

验收：一个目标跨越多个短批次并自主继续；缺料能返回采集再制作；失败能更换有依据的方法；停止后不追加写操作；聊天查询不丢失目标；预算到期明确报告剩余需求。

### P4：目标持久化与端到端验收

- 持久保存目标、计划修订、批次和动作证据摘要。记录写请求与结果不确定的状态，重启后先进入待对账状态；不自动重放合成、丢弃或存取操作。
- 长期偏好记忆可后置，但本阶段必须具备当前长目标的持久进度和恢复前对账。
- 固定世界、账号权限、版本、初始背包与公开资源场景，运行真实模型和真实服务器，记录模型调用、执行结果、耗时及最终状态。

验收任务：

| 场景 | 成功条件 | 必测变化 |
|---|---|---|
| 已有原木，无工作台 | 制作并放置工作台，制作并装备木镐 | 木材替代配方、产量批次、放置与装备 |
| 空背包，公开区域内有可达树木和暴露石头 | 获得并装备石镐 | 原木采集、木镐前置、圆石采集、多轮推进 |
| 制作一套木工具 | 持有木镐、木斧、木锹、木剑、木锄各一件 | 共享木板/木棍预算与材料不足后补采 |
| 熔炼指定数量 | 背包新增达到数量的产物 | 原料/燃料不足、等待与取出验证 |
| 中断与恢复 | 停止后无后续写操作，显式恢复后按实际状态继续 | 合成中停止、放置后中断、进程重启 |

前三个正常场景各至少 3 次独立运行，另列失败场景；保留全部尝试和失败原因。工具套装在执行前以明确列表展开，具体物品名按 1.21.1 注册表映射。测试场景提供可达公开资源不代表实现了无限世界探索。各操作和任务分别标注模拟通过/实机通过；达不到条件的能力继续保持未验收。

## 5. 推进顺序与交付纪律

先完成 P0 的合成诊断与 P1 的配方查询契约，再接 P2 的模型操作接口，随后用 P3 跑通木镐切片，最后扩展基本操作覆盖和 P4。P0 的可靠性修复与各操作接入持续交替验证，避免等到所有模块写完才进行第一次实机检查。

每阶段交付包括实现、必要的回归、文档与真实验证状态；运行 `pnpm build`、`pnpm test`，修改动作/查询 schema 后运行 `pnpm schema`。此计划不新增固定日期承诺，进度以验收证据推进。

最初交付为计划与只读数据源调研；首轮实施状态见本文开头。JEI 桥接与百科查询仍未实现；递归服务仅覆盖本地合成，完整 P0–P4 不得据此标记为完成。

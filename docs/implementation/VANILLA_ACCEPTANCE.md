# 原版两层 Agent 验收手册

版本1.0，2026-10-28。配套[实现手册](VANILLA_AGENT_V1.md)。本文全部是**待执行的验收要求**，不是测试结果；禁止提前勾选或将历史测试复制为新版本通过证据。

## 1. 验收层次

| 层次 | 依赖 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| L1 纯领域/协议测试 | 无网络、无游戏 | schema、状态、版本、预算、谓词、覆盖校验 | 模型理解能力、真实动作 |
| L2 ScriptedModel + MockBackend | 确定性脚本和故障注入 | 两层生命周期、调度、拒绝、交付和恢复逻辑 | 云模型能生成正确计划 |
| L3 真实原版隔离服 | Java/Mineflayer/专用存档 | 动作、取消、差分、多人聊天、真实副作用 | 未接云模型时不能证明NL规划 |
| L4 真实LLM + 原版服 | 用户已有供应商配置 | 中文理解、动态分解、反馈调整和端到端交付 | 小样本不能证明普遍成功率 |

UI检查单独标注，不把截图等同于功能验收。model.thinking关闭、开启、接口未提供reasoning都应能执行；系统逻辑不能依赖reasoning文本。

## 2. 夹具与运行纪律

1. 每次真实测试记录commit、工作树差异摘要/源码hash、提示词hash、依赖版本、服务器版本、世界标签、模型名、供应商、thinking/stream、全部预算。
2. 源码与提示词冻结后开始一批实验；中途改动必须新run_id，不能把两批拼为同版本成功。
3. 专用端口与存档，启动前确认无用户服务器占用。只停止本次创建的进程，不重置用户世界。
4. 配置写runtime/acceptance-v1/<run_id>/，引用原有key_file，日志不包含密钥和完整HTTP头。
5. fixture创建可由测试设施使用服务端管理接口；Bot运行期间不能拥有该接口。记录测试干预事件，不把它当Agent能力。
6. 动作结果尽量由独立于Agent判断的测试器复核；测试器不得把正确计划或答案传给Planner。
7. 失败、超时、取消、不可解析输出均计入结果，不仅保存最终成功轮。
8. 每场景恢复到声明的初始库存、箱子和位置；共享场景造成依赖时记录，不能宣称独立试验。
9. 原版受控检查和三名真实玩家手工验收可互补，手工验收记录命令、时间、任务ID和日志，不能仅凭印象。

## 5. 两个完整端到端轨迹要求

### 5.1 信息任务

输入：`!agent 描述你所处的环境`。

期望逻辑轨迹（不限定模型调用次数或措辞）：

```text
request_received(raw_chat和command_text可追溯)
observe -> evidence
Coordinator识别报告交付
若缺信息：受限观察Worker -> query -> evidence -> stage verification
ReportDraft引用观察
Contract/报告对齐与依据检查
DeliveryService提交一个或多个say
task_finished：工作验证与交付状态均明确
```

禁止轨迹：把当前坐标注册为根目标；为了通过位置谓词执行finish；输出仅“已在目标范围”；模型写了描述但未交付。

“完成”只覆盖“描述当前可观察环境”，不能在观察有限时声称完成“查明周围所有建筑”这样的更强要求。

### 5.2 制作、纠正与报告

初始执行P01，在制作证据确认后、交付前注入：`!agent 纠正 改放U箱，其他要求不变`。

期望：

1. 旧attempt被取消并核对，制作的8块成品保留。
2. 原始请求与纠正均进入新Coordinator上下文。
3. 语义版本递增，根预算与来源基线保留。
4. 建立U箱基线，计划仅处理剩余交付与报告。
5. 未再次消耗原木/制作木板。
6. U+8；T无本次交付（若取消竞态已放入T，必须按实际效果处理，不能假设未放）。
7. 报告实际来源、交付位置与任何部分效果。

## 6. L4测试设计

### 6.1 冻结测试集

核心类别：信息报告、明确移动、复合制作交付、材料保留、歧义澄清、能力不支持、反馈重规划、执行中纠正、停止。

开发用表达与验收表达分开。每类至少3种不同中文表达，部分更换物品/坐标/数量；如换到后端不支持物品应调整场景并记录，不伪造能力。不要把所有验收句子作为提示词few-shot。

最低云验收集合：N01、N02、N05及N06续接、N07、N09、P01、P03、P05、P11、C01；两个已配置供应商分别执行。每项至少一次为工程门槛；稳定性报告对信息、复合交付、纠正三类各做至少3个独立重置试验，样本小须明确。

相同任务需要多次尝试时把重试成本和首轮结果全部记录。未通过就修复后重新冻结新版本，不用删除失败记录达标。

### 6.2 长程场景

使用现有能力组合：确认来源和目标、查询配方、取料、制作中间材料、制作产物、交付、核对、报告。至少4个有真实依赖的阶段，并通过预置材料缺口或可达性变化要求一次反馈调整。

不要为凑长程而拆“思考一下”“再思考一下”等空阶段。长程度量记录实际阶段、工具提交、持续时间与有效计划修订；不只数reasoning字符。

测试预算采用专用配置，可提高到明确声明的合理值；禁止不报告地给新架构更大预算。正常配置下成本和延迟也需记录，不能只展示极高预算成功。

### 6.3 对比基线

- 修正需求表达和报告交付后的单Agent，无经验检索。
- 两层Agent，同模型、同工具、同环境、相同根预算，无经验检索。

不把已知强制near_position错误的旧提示词作为唯一对比，避免夸大层次架构收益。本版不做学习消融，不列B1/B2提升。

## 7. 指标定义

| 指标 | 定义 |
| --- | --- |
| 正确完成率 | 独立验收确认全部必需结果且回复提交的任务数 / 有执行目标的任务数 |
| 正确处理率 | 对完成、合理澄清、正确不支持分别按场景oracle判定；不得与完成率混用 |
| 错误完成率 | Bot标completed但独立验收失败的数量；同时报告占全部任务和占claimed-completed两种比例 |
| 约束违反次数 | 实际发生的违规动作/效果，不仅是被拒提议 |
| 恢复成功率 | 故障后能正确续接或正确停于需澄清的比例，分别列明，不混成完成 |
| 重复副作用 | 故障/纠正后不必要重复制作、转移等次数 |
| 成本与延迟 | 模型调用、已知tokens、usage缺失数、活动时间、工具提交和局部/全局重试 |
| 停止延迟 | stop输入至发出backend.stop、至动作稳定、至根任务收尾三个时间分别记录 |
| 报告交付率 | 必需报告已提交 / 必需报告；unknown独立列，不当失败或成功掩盖 |

模型语义审查与独立测试判定分别保存。不让被测模型自评成为唯一oracle。无固定成本价格时只报tokens/次数，不猜金额。

## 8. 报告格式

建议每个case保存：

```json
{
  "case_id": "N01",
  "run_id": "EXAMPLE_ONLY",
  "level": "L4",
  "source_commit": "TO_BE_RECORDED",
  "prompt_hash": "TO_BE_RECORDED",
  "input": "描述你所处的环境",
  "provider": "TO_BE_RECORDED",
  "model": "TO_BE_RECORDED",
  "budget": {},
  "task_refs": [],
  "claimed_end_state": null,
  "independent_verdict": "not_run",
  "checks": [],
  "evidence_refs": [],
  "usage": {"complete": false},
  "limitations": []
}
```

这只是待填格式，不能作为成功结果提交。case完整日志放runtime；公开摘要脱敏，记录hash与运行日期。未知状态保持unknown/not_run，不转成false后省略。

## 9. 发布门槛

1. 当前正式test入口与demo通过；新增场景确实被发现执行。
2. L1/L2必测矩阵全部通过，无未知用例冒充通过。
3. 原版动作原有回归通过；P01/P11和C02/C04/C08等跨层副作用用例有真实证据。
4. 两个供应商的最低L4集合实际跑完并通过对应oracle；若账户不可用，只能交“离线实现完成、云验收未完成”的阶段结果。
5. 真实测试中无错误completed、无约束违反、无重复非幂等副作用；出现一次即需修复与复验。该门槛不等于统计保证以后永不失败。
6. 面板真实显示角色/阶段/证据；停止不依赖模型返回；重启不自动重放。
7. 角色、世界、密钥、用户服务器和私有配置未被测试破坏；没有敏感文件入Git。
8. 文档与实现一致，学习/整合包仍明确延期。

不能达到门槛时报告未通过项、原因和证据，保留新模式显式启用；不要切换默认或写“全部完成”。

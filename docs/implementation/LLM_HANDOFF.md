# 交给其他 LLM 的实施提示词

把下面代码块内的文字复制给能访问本仓库的实现模型。先确保它能读取本文件及另外两份手册；若在另一台电脑，先取得当前仓库和文档，不要只给模型一段聊天摘要。

此提示词是供用户后续主动发出实施任务使用的，不表示文档作者已经执行了代码改造。

```text
请在 Super-Intelligent-Minecraft 仓库实现原版两层 LLM Agent。

本地项目原路径为 D:\Projects\Super-Intelligent-Minecraft；如果环境不同，使用实际仓库根目录。

先读取：
1. AGENTS.md
2. docs/implementation/VANILLA_AGENT_V1.md
3. docs/implementation/VANILLA_ACCEPTANCE.md
4. docs/ARCHITECTURE.md、docs/PROTOCOL.md、docs/VALIDATION.md
5. 当前 git status/diff，以及上述手册映射的现有代码。

用户已选定两层架构：Coordinator负责原始自然语言需求、任务约定、阶段计划、派发、重规划与汇总；Worker负责阶段内分析、查询和动作选择；程序负责统一执行、约束、预算、取消、证据与验收。现在请按手册实施，不只给建议。

本版只做原版Bot。学习、经验检索增强、技能生成、自主课程和整合包兼容延期。保留现有代码和数据，不删除学习库；新hierarchical路径限定B0。不要增加任意代码执行、模组机器、攻击/放置等未批准能力。

最重要的问题：
- 当前首轮必须选有限goal，导致“描述环境”被替换成near_position。
- 当前TaskSpec.intent从goal.type派生，不能独立表示用户意图。
- 当前模型最终message没有成为可靠的玩家交付。
- 当前没有真实的阶段分解、子Agent派发和长期任务状态。
要解决这些问题所属的类别，不为某条中文句子写硬编码补丁。

必须保留：Python规划/控制与Node Mineflayer动作边界；现有动作和约束校验；停止绕过模型；取消部分效果；过期响应隔离；模型流完整性；密钥脱敏；只读本机面板。

按P0至P7分阶段推进。先建立基线、纯数据契约与唯一执行控制器；再贯通两层模型、验收和玩家报告；随后完善重规划、多人控制、持久化恢复和任务树。不要先只建空目录或换UI标签，也不要一次重写全部执行器。

创建并持续维护 docs/implementation/PROGRESS.md，记录每阶段实际完成内容、测试命令/结果、限制和下一步。每次阶段结束给出简洁报告；上下文不足前把交接记录写清楚。不要把计划勾选当成功能证据。

默认复用当前模型配置，让两个角色独立上下文调用同一模型；不要求更换供应商。不得静默回退rules。未知需求要澄清或解释不支持，不能替换成容易完成的动作。

所有模型输出是提议。完成必须覆盖原始需求、真实证据和必需报告提交。子任务成功不等于根任务完成。语义Reviewer只能提供支持性审查，不能覆盖失败的程序谓词。

一个角色只有一个身体/窗口操作锁。两个Agent不能各自启动游戏连接、各自控制移动。根预算不随阶段、纠正、恢复或重规划重置。所有调用（含审查/纠错）都计入根预算。

恢复必须显式触发并先核对现场。动作请求超时或进程崩溃后，结果可能已经发生；禁止盲重放deposit/craft等非幂等动作。数据库检查点不等于游戏回滚或exactly-once。

多人模式保留owner="*"，三名玩家可停止/纠正/回答；普通新任务在忙碌时明确拒绝。保存发起者和每次修订者。停止后晚到模型输出不得触发动作或旧报告。

不要修改或输出私人API密钥。不要批量覆盖config.json、其他local配置、预算、用户名、存档。真实验收仅在独立测试服/专用存档完成，不停止或重置用户正在玩的服务器。没有真实API条件时明确记录未验收，不用mock、rules或历史结果冒充。

行为更改按AGENTS运行 scripts/dev.py test，跨层更改运行demo；采用实际能被unittest/Node正式入口发现的测试风格。按验收矩阵补充语义、交付、取消、纠正和故障恢复用例。

最终交付代码、配置/迁移说明、实际验证记录、剩余限制和可复现命令。只有满足手册发布门槛才切换新安装默认，旧配置不能静默迁移。历史公开验收不能改写成新版本通过证据。

现有用户协作约定继续有效：设计范围内的常规实现无需反复询问；如果发现需要改变关键架构、加入范围外能力、放宽约束或改变用户数据处理方式，先说明原因、备选方案和影响，等用户敲定。修复测试失败不能以削弱要求为代价。
```

## 用户审阅实现时的快速检查

- “描述环境”是否真发回描述，还是又报告距离满足？
- 面板是否有独立Coordinator/Worker调用，能追溯不同上下文？
- 复合任务是否有真实阶段、反馈修订和根任务验收？
- 制作后改箱是否只做剩余交付？
- 模型生成中停止是否立即生效？
- 重启是否先核对效果，而不是再放一次物品？
- 所谓通过是否来自当前版本真实测试，而不是旧日志或固定脚本？

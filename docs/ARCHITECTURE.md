# 基础版 Agent 的实现设计

## 目标与边界

原版 Java Minecraft 1.21.1，单个机器人、单个指令拥有者。借鉴分层控制思路：自然语言模型理解目标并决定下一步，程序执行状态机，Mineflayer 用普通玩家动作改变世界。第一版不训练模型，不做内容模组适配，不把聊天记录当成长程学习。

```
玩家 !agent 指令 / 终端 --task
          ↓ 身份、忙状态、停止指令检查
Python TaskState ← 最新世界观察
          ↓
DeepSeek：目标谓词 + 一个查询或动作
          ↓ 程序校验目标、能力、参数、预算
Python 执行控制器 ─ JSONL ─ Node/Mineflayer
          ↑                    ↓
状态轮询与目标复核      寻路 / 方块 / 配方 / 槽位
          ↓
真实完成 / 明确失败 / 取消 / 需要澄清
```

模型不直接运行代码，也不负责高频移动控制。任务未完成时控制循环继续；结束时不能许诺不存在的后台工作。

## 第一版的执行能力

| 能力 | 输入与限制 | 成功证据 |
|---|---|---|
| 观察 | 当前位置、背包、生命、附近玩家 | 当前快照，标注时间与世界标签 |
| 搜索 | 已加载区块内限定半径与数量 | 方块实际 ID、坐标和距离 |
| 移动 | 坐标与允许误差 | 最终位置进入目标范围 |
| 跟随 | 指定玩家、有限时长 | 跟随动作结束及最终距离 |
| 采集 | 方块 ID、最多采集块数 | 实际破坏与拾取变化，物品目标另行复核 |
| 合成 | 物品、所需产出数 | 游戏配方、材料消耗和实际产出 |
| 箱子存取 | 已知坐标、物品、精确数量 | 角色和容器的实际数量变化 |
| 熔炉 | 坐标、原料、燃料、数量、等待上限 | 实际产物取出，超时保留部分进度 |

寻路不自动挖路、搭柱或放方块。完整从零生存仍取决于工具、可达地形和已实现操作；第一版不承诺任意建筑、战斗、维度穿越或任意 GUI 操作。

## 高层闭环

1. 接收任务后读取当前状态。模型将用户要求落为可检查的目标，并提出一步动作。
2. 程序锁定目标，检查工具白名单、参数类型和范围，拒绝不受支持的目标类型。
3. Node 返回 action_id。Python 轮询状态，在此期间无需重复请求模型。
4. 将动作的前后状态、变化和错误交给高层。失败原因未知时保留未知，不归咎于距离或缺料。
5. 程序检查任务目标。达到目标才完成；没有达到则用最新观察继续规划。
6. 两次相同失败、步数或时间耗尽后退出并报告卡点。停止指令先取消底层，再使迟到的模型结果失效。

目标数量明确区分“背包总共达到 N 件”与“在本次任务新增 N 件”。容器目标必须检查指定容器，移动目标必须检查坐标；一个普通 success 标志不能覆盖所有目标。

## 协议和状态

详细契约见 [PROTOCOL.md](PROTOCOL.md)。两进程通过标准输入输出 JSON Lines 通信，避免额外 HTTP 服务与密钥。Node 日志只写 stderr。观察和动作结果有时间戳；任务日志保留状态变化、模型用量与失败证据。

每个动作有 running / succeeded / failed / cancelled。取消与超时并不回滚已经发生的挖掘或物品转移，报告必须保留真实部分结果。旧动作没有完全退出前禁止开启另一个会改变世界的动作。

## 后续的学习能力

第一阶段先做可靠的执行与验证。第二阶段再把通过检验的轨迹抽成带前置条件、适用版本和失败条件的技能，检索给规划器参考。未经验证的模型总结不写成成功技能。经验库不能弥补底层缺失操作。

建议里程碑：M1 打通移动/物品闭环 → M2 多步自然语言任务与取消 → M3 可复用技能及对照实验。当前实现和实测进度以 README 与验收日志为准。

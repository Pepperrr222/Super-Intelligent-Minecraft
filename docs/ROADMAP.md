# 开发路线与验收条件

这是计划，不是已完成清单。当前进度以 [PROJECT_STATUS.md](../PROJECT_STATUS.md) 为准。

## 当前节点：底层原型已实现，等待实机验证

现有43个动作、5种查询、41项自动测试，以及42工具/100题静态分析，构成后续开发的基础。部分机制仍返回UNSUPPORTED或只提供局部积木；不能将整个底层阶段标记为完成。

## 1. 验证最小动作集

在版本固定的Minecraft Java1.21.6自有测试服中，先验证连接/出生、观测、移动/导航、停止、装备、挖掘、拾取观测、放置、合成、容器和熔炉。交易、附魔、铁砧、酿造与载具随后逐组验证。

每次记录实际服务器/依赖版本、初始状态、动作参数、结果、最终世界/背包状态、取消清理和失败原因。测试输入使用公开场景，不把隐藏判分数据给Agent。

验收：最小动作集在固定场景可重复执行；成功、失败、超时、取消与断线均有真实记录。缺陷修复后补对应回归，明确仍不支持的动作。没有实测记录的动作保持not_run。

## 2. 建立第一批组合技能

跟随玩家、靠近玩家、坐标导航和背包查询已有确定性原型及模拟测试；下一步实现采集并拾取指定资源、制作指定数量、熔炼指定数量和存入指定箱子。现有smeltBatch仅作为组合示例，不直接提升为完整技能库。

每项技能定义输入、前置条件、步骤、后置条件、部分效果、失败与停止语义。目标选择、导航接近、工具选择、材料检查属于这一层。

验收：使用确定性输入在游戏内完成技能并验证真实结果；能响应停止；遇到背包满、路径不可达、材料不足时明确退出，不把“已发出动作”写成“任务完成”。

## 3. 实现任务调度与状态

在现有单动作租约之上建立任务队列、task_id、任务阶段、优先级、取消、暂停与恢复。逐步增加持久动作记录和revision，恢复前先与世界和背包对账。

验收：两个任务不会同时控制机器人；停止旧任务后不会继续发出后续写操作；重启后能辨认已发生的副作用，避免重复交易、消耗或交付。

## 4. 接入玩家交互和伙伴大脑

先接玩家聊天监听、交互对象识别和结构化技能入口，再接模型进行自然语言理解与规划。所有游戏写操作通过调度器和动作层。

验收：玩家发出“跟着我”“帮我收集指定资源”“停下”等请求，可看到理解、执行、反馈和中断的完整闭环；失败时给出可核验原因；模型不能绕过动作约束或直接伪造成功。

## 5. 记忆、复杂玩法与画布

在稳定闭环上补玩家偏好、地标、共同经历和计划恢复；按实际需求扩展建造、战斗、特殊GUI与载具控制器。节点画布将真实技能封装为可展开子流程，并显示运行进度。

验收：画布节点连接到实际模块，取消与错误可以传回界面；持久记忆可追溯来源；新玩法有独立版本适配和实测记录。

## 6. 基准评测

再完成CoCraftBench请求/返回协议、版本与身份契约，并配合独立测试世界、运行器和服务器grader。任务成功率与工具缺口分开报告，未实现项保留在原定分母中。

验收：能复现完整episode及证据记录；工具局部成功与任务最终判分分离；具备基于真实运行的结果，而不只是一份接口覆盖表。

以上阶段可以在接口明确后部分交错推进；近期重点是最小动作集实测与一个组合技能闭环，不继续用动作数量代替可用性进展。

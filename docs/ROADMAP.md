# 开发路线与验收条件

这是计划，不是已完成清单。当前进度以 [PROJECT_STATUS.md](../PROJECT_STATUS.md) 为准。

2026-11-05 sim-v2-8：已按用户要求删除方案模型复核和回复模型复核，当前仅理解/主控/执行/最终验收四个角色。下一步实机比较从“砍树”输入到第一步动作的时间、总模型调用数、引用错误和最终原木数量；328 项模拟回归通过不代表真实语义与执行成功率已验收。

持续阶段解释器已实现并通过模拟及两项真实模型生成方案检查，下一步验收真实服务器中的连续采集/掉落拾取、搬运、工作台放置后制作、跟随/等待，以及中途新指令与断线恢复。比较模型调用、动作间停顿、错误恢复和完整任务成功率；不把模拟动作数转换为实机性能承诺。方案复杂度、存储归档容量和更多真实模型语义样本仍需持续评估。接口见 [阶段执行](stage-execution.md)。

近期必须补真实模型语义回放：独立新任务替换暂停旧目标、数字修正不叠加、过程采集与最终持有区分，以及相同方法续做。脚本 LLM 回归只能验证程序协议，不能作为中文路由正确率或真实整任务稳定性的证据。对“采集并制作”记录从新目标建立到最终验收的完整调用/动作链，再比较失败率和消耗。

## 近期主线：基本操作 + 长程规划

2026-11-01 根据用户明确的阶段目标调整优先级。详细实施顺序、JEI/本地配方/百科取舍、递归依赖查询及验收场景见 [基本操作与长程规划开发计划](basic-operations-long-horizon-plan.md)。首轮已实现本地配方/递归查询、模型知识查询接线和精确配方制作，只有模拟验证；P0 实机验收、P2 通用操作网关与 P3/P4 仍未完成。

推进顺序：P0 基本操作实机诊断（优先合成与背包对账）→ P1 理论配方与递归需求查询 → P2 开放 LLM 可指定的基本操作及观测引用 → P3 持续目标与滚动规划 → P4 目标持久化、恢复对账和实机验收。首个纵向切片是“已有原木 → 制作并放置工作台 → 制作并装备木镐”，随后完成空背包到石镐、多工具共享材料和熔炼。

现有组合技能保留为可选便捷工具；模型可通过结构化接口选择基本操作和配方，所有写操作仍由同一个动作执行器处理。JEI 桥接作为可选数据源，先使用当前版本本地配方；百科仅补充知识。节点画布、多 Bot 与基准协议适配后置。

下列阶段保留总体能力与验收条件，近期执行顺序以 P0–P4 详细计划为准。

## 当前节点：底层原型已实现，等待实机验证

现有44个动作、8种查询、235项自动测试，以及42工具/100题静态分析，构成后续开发的基础。本轮新增17项配方知识、递归需求、精确制作和模型查询回归；其中61项覆盖此前的决策循环。部分机制仍返回UNSUPPORTED或只提供局部积木；不能将整个底层阶段标记为完成。

## 1. 验证最小动作集

在版本固定的 Minecraft Java 1.21.1 自有测试服中，先验证连接/出生、观测、移动/导航、停止、装备、挖掘、拾取观测、放置、合成、容器和熔炉。交易、附魔、铁砧、酿造与载具随后逐组验证；现有仅支持 1.21.6 的接口保持版本限制，不推断为兼容 1.21.1。

每次记录实际服务器/依赖版本、初始状态、动作参数、结果、最终世界/背包状态、取消清理和失败原因。测试输入使用公开场景，不把隐藏判分数据给Agent。

验收：最小动作集在固定场景可重复执行；成功、失败、超时、取消与断线均有真实记录。缺陷修复后补对应回归，明确仍不支持的动作。没有实测记录的动作保持not_run。

## 2. 建立第一批组合技能

跟随玩家、靠近玩家、坐标导航和背包查询已有确定性原型及模拟测试。首批七个动态技能（`find_resource`、`navigate_to`、`collect_drops`、`gather_wood`、`craft_item`、`store_items`、`deliver_to_player`）已实现并通过模拟测试，但尚未完成本阶段要求的游戏内验收；熔炼指定数量仍未成为完整技能。现有smeltBatch仅作为组合示例，不直接提升为完整技能库。

每项技能定义输入、前置条件、步骤、后置条件、部分效果、失败与停止语义。目标选择、导航接近、工具选择、材料检查属于这一层。

验收：使用确定性输入在游戏内完成技能并验证真实结果；能响应停止；遇到背包满、路径不可达、材料不足时明确退出，不把“已发出动作”写成“任务完成”。

## 3. 实现任务调度与状态

在现有单动作租约之上建立任务队列、task_id、任务阶段、优先级、取消、暂停与恢复。逐步增加持久动作记录和revision，恢复前先与世界和背包对账。

验收：两个任务不会同时控制机器人；停止旧任务后不会继续发出后续写操作；重启后能辨认已发生的副作用，避免重复交易、消耗或交付。

## 4. 接入玩家交互和伙伴大脑

先接玩家聊天监听、交互对象识别和结构化技能入口，再接模型进行自然语言理解与规划。所有游戏写操作通过调度器和动作层。

当前进展：统一决策循环、程序校验、`RunFeedback`、单目标预算、有界跟进和模型侧取消/替换已实现（模拟测试）；配置推理模型时启用，否则保留旧的小模型路由。新决策提示词已在真实服务器上做过少量初步现场观察，但尚未完成系统评测或按手册验收。

验收：玩家发出“跟着我”“帮我收集指定资源”“停下”等请求，可看到理解、执行、反馈和中断的完整闭环；失败时给出可核验原因；模型不能绕过动作约束或直接伪造成功。

## 5. 记忆、复杂玩法与画布

在稳定闭环上补玩家偏好、地标、共同经历和计划恢复；按实际需求扩展建造、战斗、特殊GUI与载具控制器。节点画布将真实技能封装为可展开子流程，并显示运行进度。

验收：画布节点连接到实际模块，取消与错误可以传回界面；持久记忆可追溯来源；新玩法有独立版本适配和实测记录。

## 6. 基准评测

再完成CoCraftBench请求/返回协议、版本与身份契约，并配合独立测试世界、运行器和服务器grader。任务成功率与工具缺口分开报告，未实现项保留在原定分母中。

验收：能复现完整episode及证据记录；工具局部成功与任务最终判分分离；具备基于真实运行的结果，而不只是一份接口覆盖表。

以上阶段可以在接口明确后部分交错推进；近期以 P0–P4 计划推进基本操作可靠性、灵活调用与持续目标规划，用实机任务结果衡量进展。
